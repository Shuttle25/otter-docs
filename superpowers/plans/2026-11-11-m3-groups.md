> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers-extended-cc:subagent-driven-development (recommended) or superpowers-extended-cc:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** End-to-end encrypted group chats (up to 100 members) with admin-signed membership, sender-key rotation
on removal and per-recipient delivery details. The Otter design assets are integrated (launcher icon, welcome, empty
states, family-group avatar, coloured initials). The message context menu opens above the pressed message instead of
at the left edge.

4. `docs/superpowers/plans/2026-11-11-m2-mesh.md` for the plan format and for what exists.

**Architecture:** Groups are **client-side state**. Nodes only fan out envelopes. Group state (`GroupState`: id, name,
members, admins, version, family flag) travels **inside** E2E 1:1 messages as a `SignedGroupState`, signed with the admin's
Ed25519 account key. Each client applies deterministic acceptance rules (`GroupRules`, pure Kotlin) and parks updates it
can't verify yet. Group messages use libsignal **Sender Keys**: each member has its own sender key per group
(`distribution_id`), and sends its `SenderKeyDistributionMessage` (SKDM) 1:1 to every member who lacks it, before its
first group message. A group message is **one** ENVELOPE (`kind = SENDER_KEY`, `shared_content` = ciphertext, recipients =
all other members). When a member is removed, everyone switches to a new `distribution_id` (rotation), so the removed member
can't read later messages. Receipts stay 1:1 to the sender; the sender aggregates them per recipient (D23).

**Decisions (made with the owner on 2026-11-11; Task 14 records them as D33–D38 in `docs/00-decisions.md`):**
- **D33 Admin rights:** the creator is admin; admins add, remove, rename and promote other admins; any member may leave. If the
  last admin leaves, they must first promote someone (UI enforces it; the rules reject a state without admins).
- **D34 Family groups:** a group is marked **"Семейная группа" manually by its creator** at creation (immutable flag). Several
  family groups may exist, because one network may serve several families. Members are added by hand; invited people are
  **not** added to any group automatically. Family groups show `otter_family_avatar`; every other group and every person shows
  coloured initials. The colour comes from the stable id, not the name.
- **D35 History:** new members see only messages sent after they joined (sender keys are shared from the current iteration).
- **D36 Ordering:** a group update whose signer isn't (yet) an admin in the local state, or that skips versions, is parked and
  retried after every accepted update (expires after 30 days).
- **D37 Concurrent edits:** at equal version, the state signed by the lower `user_id` wins (it must be valid against the
  common previous state); further ties are broken by the lower SHA-256 of the state bytes.
- **D38 Message menu:** the long-press menu opens above the pressed bubble, aligned to the bubble's side. It flips below when
  there's no room above.

**Tech Stack:** as M2. Python 3 + Pillow (already installed, WebP supported) for the asset export script only.

**Out of scope:** group photos/custom avatars, mentions, reply-quotes (later), push (M5), group invite links,
username-conflict UI (M8).

```kotlin
package app.ottermsg.core.ui.components

/** Pure placement used by [AnchoredMenu]; exposed for tests. */
fun anchoredMenuOffset(anchor: IntRect, window: IntSize, popup: IntSize, alignEnd: Boolean, gapPx: Int): IntOffset {
    val maxX = (window.width - popup.width).coerceAtLeast(0)
    val x = (if (alignEnd) anchor.right - popup.width else anchor.left).coerceIn(0, maxX)
    val maxY = (window.height - popup.height).coerceAtLeast(0)
    val above = anchor.top - gapPx - popup.height
    val below = anchor.bottom + gapPx
    val y = when {
        above >= 0 -> above
        below <= maxY -> below
        else -> 0
    }
    return IntOffset(x, y.coerceIn(0, maxY))
}

private class AboveAnchorProvider(private val alignEndLtr: Boolean, private val gapPx: Int) : PopupPositionProvider {
    override fun calculatePosition(anchorBounds: IntRect, windowSize: IntSize, layoutDirection: LayoutDirection, popupContentSize: IntSize) =
        anchoredMenuOffset(anchorBounds, windowSize, popupContentSize,
            alignEnd = if (layoutDirection == LayoutDirection.Ltr) alignEndLtr else !alignEndLtr, gapPx = gapPx)
}

data class MenuAction(val label: String, val onClick: () -> Unit)

/** Place inside the composable it should anchor to (e.g. a Box wrapping the bubble Surface). */
@Composable
fun AnchoredMenu(expanded: Boolean, alignEnd: Boolean, actions: List<MenuAction>, onDismiss: () -> Unit) {
    if (!expanded) return
    val gap = with(LocalDensity.current) { Dimens.s8.roundToPx() }
    Popup(popupPositionProvider = remember(alignEnd, gap) { AboveAnchorProvider(alignEnd, gap) },
        onDismissRequest = onDismiss, properties = PopupProperties(focusable = true)) {
        Surface(shape = RoundedCornerShape(Dimens.s12), tonalElevation = 3.dp, shadowElevation = 3.dp,
            color = MaterialTheme.colorScheme.surface) {
            Column(Modifier.width(IntrinsicSize.Max).widthIn(min = 160.dp).padding(vertical = Dimens.s4)) {
                actions.forEach { a ->
                    Box(Modifier.fillMaxWidth().heightIn(min = Dimens.minTouch)
                        .clickable { onDismiss(); a.onClick() }.padding(horizontal = Dimens.s16),
                        contentAlignment = Alignment.CenterStart) {
                        Text(a.label, style = MaterialTheme.typography.bodyLarge)
                    }
                }
            }
        }
    }
}
```

### Task 4: Content protos and `GroupRules`

**Goal:** Group wire formats and the pure acceptance rules, fully unit-tested.

**Acceptance Criteria:**
- [ ] Protos:
```proto
message Content {
  oneof body {
    DataMessage data = 1;
    ReceiptMessage receipt = 2;
    GroupUpdate group_update = 3;
    SenderKeyDistribution sender_key = 4;
  }
  int64 sent_ms = 10;
}
message DataMessage { bytes message_id = 1; string text = 2; GroupContext group = 3; }
message GroupContext { bytes group_id = 1; }
message GroupState {
  bytes group_id = 1;           // 16 random bytes
  string name = 2;              // 1–64 chars, trimmed
  repeated bytes members = 3;   // user ids, unique, 1–100
  repeated bytes admins = 4;    // subset of members, non-empty while members non-empty
  uint64 version = 5;           // 1 at creation, +1 per change
  bool family = 6;              // D34, immutable
  bytes created_by = 7;         // immutable
  int64 created_ms = 8;         // immutable
}
// signature = Ed25519(signer account key, "otter-group-v1" || state)
message SignedGroupState { bytes state = 1; bytes signer = 2; bytes signature = 3; }
message GroupUpdate { SignedGroupState state = 1; }
message SenderKeyDistribution { bytes group_id = 1; bytes distribution_id = 2; bytes message = 3; }
```
- [ ] `GroupSigning.sign(state, account)` / `verify(signed, accountPub)` (prefix `otter-group-v1`)
- [ ] `GroupRules.evaluate(current: Applied?, previous: GroupState?, candidate: GroupState, signer: ByteArray): Verdict` with
  `Verdict = Accept | Reject(reason) | Park(reason)` and structural checks (sizes, uniqueness, admins ⊆ members, immutables unchanged):
  - no current: accept only `version == 1 && signer == created_by && signer ∈ admins`; else **Park** (we may have missed the creation)
  - `candidate.version == current.version + 1`: accept if signer ∈ current.admins; or if it's a **self-leave** (candidate = current minus signer in members and admins,
    name unchanged, signer ∈ current.members, and admins still non-empty unless members are empty); else **Park** if signer ∉ current.members, else Reject
  - `candidate.version > current.version + 1`: accept if signer ∈ current.admins (missed steps are irrelevant for an admin), else Park
  - `candidate.version == current.version`, different bytes: compare against `previous` (both must be valid successors of it); the lower signer id wins,
    then the lower SHA-256(state); the loser → Reject("superseded")
  - `candidate.version < current.version` → Reject("old")
- [ ] Tests (table-driven): create; admin add/remove/rename/promote; non-admin change rejected; self-leave accepted; leave that changes the name rejected;
  last admin leaving while others remain rejected; version gap by admin accepted; gap by non-admin parked; concurrent equal versions resolve identically in both
  orders; immutable `family`/`created_by` change rejected; 101 members rejected; duplicate member rejected

### Task 7: `core:data` — group state management

**Goal:** Create and change groups locally, distribute signed updates, apply incoming ones with the rules, record system events, trigger rotation.

**Files:** Create `core/data/.../group/{GroupRepository,GroupApplier,GroupEvents}.kt`; Modify `messaging/MailboxReceiver.kt`

**Acceptance Criteria:**
- [ ] `GroupRepository`: `create(name, family, members)`, `addMembers`, `removeMember`, `rename`, `setAdmin(user, admin)`, `leave()`. Each builds the next state
  (version + 1), signs it, and applies it locally **through the same `GroupApplier`** as incoming updates. It then enqueues a `GroupUpdate` 1:1 (urgent = true) to every

  Reject: drop (log). After every Accept, retry all parked updates for that group until none is accepted
- [ ] System events (stored as `messages` rows, kind `SYSTEM_GROUP`, `system_data` = proto `GroupEvent{type, actor, targets, name}`): created, added, removed, left,
  renamed, admin granted/revoked, "you were removed". Event types are rendered by the UI (Task 10), never stored as text
- [ ] **Rotation trigger:** when an accepted state removes anyone (removed or left), delete `my_distribution` for that group (a new distId is created on the next send,
  see Task 8) and clear `sender_key_shared` for it
- [ ] Removed (or left) self: `i_am_member = false`, conversation stays readable, the composer is disabled (Task 10)
- [ ] Adding members: their 1:1 sessions are established lazily by the outbox like any 1:1 message (prekeys fetched on demand)

### Task 8: `core:data` — group messaging and receipts

**Goal:** Send and receive group messages; per-recipient delivery state.

**Files:** Create `messaging/GroupSender.kt`, `messaging/GroupReceiver.kt`; Modify `Outbox.kt`, `MailboxReceiver.kt`, `MessageRepository.kt`, `Receipts`
logic; tests

**Acceptance Criteria:**
- [ ] `MessageRepository.sendText(conversationId, text)` for a group conversation: one transaction inserts the message (PENDING), `message_recipients` rows
  for the **current members except me** (the frozen recipient set, D23), and **one** outbox item with `group_id`
- [ ] Outbox, group item, first processing: (1) ensure `my_distribution` exists (new random UUID if missing); (2) for every current member lacking a row in
  `sender_key_shared` for that distId, enqueue a 1:1 `SenderKeyDistribution` **ahead of this item**, record the shares, and defer this item until those are sent
  (re-schedule; no busy loop); (3) encrypt `Content{data{message_id, text, group{group_id}}}` with `GroupSessions.encrypt(distId)`; build an ENVELOPE (`SENDER_KEY`,
  `shared_content`, recipients = the frozen recipient set) and persist the signed record (same "encrypt once" rule as 1:1)
- [ ] If membership shrank between enqueue and send, recipients are still the frozen set minus removed members (never send to a removed member)
- [ ] Receive `SENDER_KEY`: decrypt via `GroupSessions.decrypt(senderAddress, shared_content)`. `NoSessionException` or unknown group → store in `pending_group_envelopes`
  and **ack** (the node's copy isn't needed any more). After processing a `SenderKeyDistribution` or an accepted group state, retry the pending envelopes from that sender
  or for that group. Pending entries older than 7 days → system "undecryptable" message
- [ ] After decrypt: `content.data.group.group_id` must be a group where the sender ∈ members and I ∈ members (my state); otherwise drop (logged). Insert the message
  into the group conversation (author = sender), unread++, DELIVERED receipt 1:1 to the sender (`urgent = false`)
- [ ] Receive `SenderKeyDistribution` (1:1): `GroupSessions.process(sender, message)`, then retry pending envelopes
- [ ] Receipts: a receipt for a message I sent to a group updates that message's `message_recipients` row for the receipt's author **only if** that author is in the
  row set (otherwise ignored). The message status becomes DELIVERED when all rows have `delivered_ms`, READ when all have `read_ms` (READ implies delivered).
  1:1 behaviour unchanged
- [ ] `markConversationRead(groupConversation)` sends READ receipts grouped **per sender** (one receipt message per sender)
- [ ] 24 h resend works for group items (same record); outbox rows are deleted when the aggregate reaches DELIVERED
- [ ] Integration tests (Robolectric, real libsignal, `FakeNode` extended to fan out SENDER_KEY envelopes), 5 clients A–E:
  1. A creates group {A,B,C,D} → all have the group, title, members; system "created" event
  2. B sends "привет" → A, C, D decrypt it; B's message reaches DELIVERED after all 3 receipts; "2 of 3" visible before the last one
  3. A adds E → E receives later messages but **not** earlier ones (D35); E's first message to the group works
  4. A removes C → everyone rotates; C can't decrypt the next message (stays pending → undecryptable after 7 days of virtual time); C's conversation shows
     "you were removed" and its composer is disabled
  5. D leaves → accepted by all; the remaining senders rotate
  6. Out-of-order updates: v3 (signed by B after A promoted B in v2) delivered before v2 to D → parked, then applied after v2
  7. Concurrent: A renames to "X" and B renames to "Y" at the same version → all clients converge to the same name
  8. A group message arriving before its SKDM → pending → decrypted once the SKDM arrives; exactly one message shown
