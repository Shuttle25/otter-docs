# 00 — Decisions Log

Record of the design discussion (2026-11-10). Each entry: the question, the answer, and why.
Items marked **[proposed]** were decided by the designer while writing the docs and still need
explicit user confirmation.

## Requirements (from discussion)

| # | Topic | Decision | Rationale |
|---|-------|----------|-----------|
| D1 | Audience | Private use, friends & family, ~10–100 users, self-hosted | Shapes everything: no big-scale infra, SQLite is enough, admin is a trusted person |
| D2 | Meaning of "1/2/3 servers" | **Redundancy & failover.** 1 node is a complete system; 2–3 nodes are identical replicas. Nodes inter-communicate and relay for each other if some links are blocked. App connects to any node via the fastest working link | Survive hosting outages and partial blocking |
| D3 | Blocking threat | **Active DPI** (traffic classification, protocol fingerprinting, IP/SNI blocking, throttling of foreign hosting) **plus** hosting outages | Transport must look like ordinary HTTPS / blend in; multiple entry points; mesh relays around blocks |
| D4 | Encryption between servers | Required. Two layers: E2E (servers never see plaintext) + every link (client↔node, node↔node) encrypted and mutually authenticated with pinned keys | Defence in depth; relayed traffic is ciphertext inside an authenticated tunnel |
| D5 | V1 features | Text, 1:1 + group chats, delivery/read receipts, push, photos. *(Files and voice messages: protocol-ready, UI later — see D18)* | Fits store-and-forward mesh |
| D6 | Calls | **V2** (voice/video). Transport layer kept pluggable so a real-time media path can be added | Calls roughly double networking complexity under DPI |
| D7 | Notifications | **Most battery-friendly**: FCM data-less wake-up by default; automatic fallback when Google services are missing or FCM is blocked | Shared Google connection costs ~0 battery |
| D8 | Registration | **Invite-only** (QR/link), no phone number, no SMS, no email. Identity = key on device. Server-side member directory | Closed circle; invite also performs initial key verification |
| D9 | Devices / recovery | One device per account in V1 + **24-word recovery phrase** (restores identity) + **password-protected history backup** stored encrypted on the mesh (restores history on a new phone with username + password) | User wants working history recovery, preferably by password |
| D10 | Overall approach | **Custom stack**: Go node mesh + Kotlin Android app + libsignal + embedded Xray-core | Only option where redundancy, mesh and DPI resistance are core, not bolted on. Rejected: Matrix fork (no per-account multi-server replication, huge codebase), XMPP/ejabberd cluster (needs low-latency reliable inter-node links) |
| D11 | Server language | **Go** — single static binary, runs on any Linux the user has | Embeds Xray-core natively; easy cross-compile (amd64/arm64) |
| D12 | Node model | All nodes identical, no primary. Servers are **untrusted relays**: every record is signed by its author | A compromised node can drop/delay, but not read or forge |
| D13 | Name | **OtterMSG** (app id `app.ottermsg`; binaries `otter-node`, `otter-admin`) | User choice |
| D14 | Profile visibility | Username and display name **visible to nodes** (plaintext in directory) | Simplicity; nodes already see metadata; closed trusted circle |
| D15 | Distribution | **APK** (direct download) to start; Google Play not planned for V1 | Private circle; no store review needed |
| D16 | Admins | **Only the owner**, with the network admin key shareable with one more person (wife). Key file encrypted with a passphrase; both copies are equivalent | Two trusted admins, no extra multi-admin machinery |
| D18 | V1 media in UI (supersedes D5 UI scope) | **Photos only** in the V1 interface (gallery + camera, one photo per send). Protocol/node keep generic blobs, so files and voice messages are a later UI-only milestone | Design guide (doc 10) — simpler, calmer V1 |
| D19 | Network invites | **Any member** may invite. Directory entry carries `can_invite` (default true); admins can revoke it by a network-signed record; nodes enforce it. Unrelated to group admin roles | Design guide §10/§15.5 |
| D20 | UI language | **Russian (primary) + English** fallback; all strings in resources | Design guide is Russian |
| D21 | Display name | Launcher/top bar show **Otter**; project, binaries and app id remain OtterMSG / `app.ottermsg` | User choice |
| D22 | Reactions, typing | **Not in V1** (hidden). Need protocol events first | Design guide §1 |
| D23 | Group receipts | Recipient set fixed at send time (excluding sender). Message shows DELIVERED when all recipients delivered, READ when all read; "Message info" shows "Delivered 2 of 3". Members added later are not counted; removed members stay in the set but are marked | Design guide §8, §15.3 |
| D24 | Media availability | Nodes keep a media blob until all recipients fetched it or 30 days. After that the **phone's encrypted local copy is the only copy** (plus the backup if "include media" is on). "Clear cache" removes only temporary decrypted files and thumbnails regenerable from local originals | Design guide §9, §15.4 |
| D25 | Node addressing | Every node has a **domain name**; the owner manages DNS by hand (separate providers); `otter-admin dns records` prints the A/AAAA records. No CDN | Apps connect by name, so an IP change needs only a DNS update |
| D26 | Ports | Nodes **don't use 80/443**; one configurable rare port per node, default **27443/tcp** (not IANA-registered, not in nmap's service list, below the Linux ephemeral range). 8443 rejected: registered and widely used | Coexists with other services; no root privileges. Trade-off: easier to single out than 443 (revisited in M7) |
| D27 | TLS | **Self-signed certificate per node** (ECDSA P-256, 10 years) generated by `otter-admin`; SHA-256 SPKI **pins in the signed manifest**; the app trusts only pinned keys. No Let's Encrypt, no DNS API tokens | Manual DNS + no 80/443 rules out automatic ACME; pinning is also stronger than CA trust |
| D28 | Hosting & packaging | Hetzner VPS, Linode VPS, bare-metal Debian/Ubuntu; static binary + systemd, no Docker, no reverse proxy | Owner's infrastructure; fewest moving parts |
| D29 | Peer session per node pair | One session per pair; if both nodes dialed, both keep the session **dialed by the lower node_id** (same direction → the newest) | Both ends compute the same result without coordination; either side can dial, so one-way blocking still works |
| D30 | No snapshot protocol | Replication always streams the oplog from the peer's cursor; there is no `cursor_too_old`/snapshot path | The oplog only loses rows of deleted records and all deleted kinds expire after the same 30 days, so any cursor converges; less code. A `created_ms` retention guard stops re-sent expired records from resurrecting |
| D31 | Username clash across a partition | The lower `(directory entry created_ms, user_id)` keeps the name; the other user becomes `name#<hex(user_id[:4])>` on every node. No UI until M8 (rename screen) | Deterministic and order-independent; nobody loses their account |
| D32 | Replication lag is retryable | An unknown user at login, an unknown recipient, or missing prekeys → `STATUS_RETRY_LATER` (clients back off or try another node), not UNAUTHORIZED/NOT_FOUND; peers stop a session without advancing the cursor on a record whose author has not arrived yet | A freshly registered user or message may reach one node seconds before another |
| D33 | Group admin rights | The creator is admin; admins add, remove, rename and promote/demote admins; any member may leave. The last admin must promote someone before leaving while others remain (UI enforces it; the rules reject a state without admins) | Simple model for families; no group can end up without someone able to manage it |
| D34 | Family groups and avatars | "Семейная группа" is set **by the creator at creation** (immutable flag in the signed state); several family groups may exist (one network can serve several families). Members are added by hand, never automatically. Family groups show `otter_family_avatar`; every other group and every person shows coloured initials, colour from the stable id (not the name) | No inference from names; colours survive renames |
| D35 | Group history | New members see only messages sent after they joined (sender keys are shared from the current chain position) | Matches sender-key semantics; no history transfer |
| D36 | Group update ordering | An update whose signer is not (yet) an admin in the local state, or that skips versions without an admin signer, is **parked** and retried after every accepted update; parked updates expire after 30 days. A client that has no state for a group accepts a state signed by an admin **of that state** (trust on first use) so members added later can join | Updates travel 1:1 and can arrive out of order |
| D37 | Concurrent group edits | At equal version, the state signed by the lower `user_id` wins (both must be valid successors of the common previous state); further ties: lower SHA-256 of the state bytes | Every client converges on the same state without coordination |
| D38 | Message menu | The long-press menu opens above the pressed bubble, aligned to the bubble's side (end for own, start for incoming); it flips below when there is no room above, and goes to the top of the window when neither fits | Keeps the menu next to the message the user touched |
| D39 | Profile scope in V1 | The profile is the **display name** only (1–64 Unicode code points, plaintext in the directory per D14). The username can't be changed (a rename comes with the username-conflict screen in M8). Profile photos need blobs (M4) and encrypted profiles (V2); the avatar stays coloured initials. A name edit is saved on the phone at once and published as a newer `DIRECTORY_ENTRY` (`directory.update`) when online; until then Profile shows a note | Works offline; reuses directory replication and the existing contact-name updates |
| D40 | `DirectoryEntry.registered_ms` | Time of the first registration, copied into every later version (validators: ≤ `created_ms` + 5 min). Username clashes (D31) rank by `registered_ms`, or by the record's `created_ms` when 0 (entries from M1–M3). `directory.update` refuses a changed username (`INVALID`) and a version that isn't newer (`CONFLICT`); a member who already lost a clash (`name#hex`) may still update with the original username | A profile update must never change who keeps a username |
| D41 | `otter-node backup` and `check` in M1.5 | `backup` = `VACUUM INTO` (consistent while running; no `sqlite3` CLI on servers); `check` verifies config, node key, manifest, endpoint path and TLS pin without opening the database. Moved from M8 | The upgrade rollback needs a DB copy; install needs a config check before start |
| D42 | TLS rotation files | `node rotate-tls` stages `tls.new.{crt,key}` and adds its pin next to the old one; bundles use the staged pair when present; `node drop-old-pins` promotes it (old pair kept as `tls.old.*`) and leaves only the new pin. `node set-ip` re-issues the certificate **with the same key**, so the pin doesn't change | Pins stay valid through IP moves; rotation never strands apps |
| D43 | Scripts and admin directory | Every script honours `OTTER_ADMIN_DIR` (default `~/.otter-admin`), `OTTER_SSH_PORT`, `OTTER_SSH_OPTS`; server-side helpers live in `/usr/local/lib/otter/`; `/etc/otter/probe.env` holds the URL, pin and node id the health check uses (`--addr 127.0.0.1:<port>`, so it works before DNS is updated) | One layout for scripts, tests and the VM run |
| D44 | Blob identity and integrity | The blob key is the record key of its `BLOB_META` (`author‖id`, 32 bytes), so nobody can pre-empt someone else's blob. `BLOB_META` lists the SHA-256 of every 256 KiB chunk; nodes verify every chunk (from a client or a peer) before storing it. Limits (node config `[limits]`): `max_blob` 100 MiB, `user_quota` 2 GiB of live blobs per author (decides P13); over the limit → `STATUS_QUOTA`. Readers 1–100, never the author; expiry ≤ 31 days after `created_ms` | Integrity without trusting peers; per-author quota on what is actually stored |
| D45 | Blob lifetime and transfer between nodes | A reader publishes `BLOB_FETCHED` (record type 14) after a verified download. When every reader has one, or the blob expires, every node deletes the blob (rows, record, files) and keeps a tombstone until expiry + 1 day, so a lagging peer can't resurrect it. Nodes pull missing chunks in the background from any peer that has them (`[replication] blob_bandwidth`, default 2 MB/s; a blob no peer has yet is retried after 1 s doubling to 30 s) and fetch a missing chunk at once when a reader asks for it (and keep it). `blob.get` on a blob the node hasn't heard of → `RETRY_LATER` (D32); on a deleted one → `NOT_FOUND`. Older peers ignore the new peer frames (requests time out after 10 s) | Photos travel the mesh like messages; nodes keep them only until delivered |
| D46 | Encryption and storage on the phone | Each blob has a random 32-byte key; ciphertext = Tink `AesGcmHkdfStreaming` (HMAC-SHA256, 32-byte keys, 1 MiB segments) with the blob key as associated data. The `Attachment` in the E2E content carries the key, the SHA-256 digest and size of the ciphertext, the dimensions and a ≤ 4 KiB thumbnail. The phone keeps the ciphertext file in `filesDir/media/` as the encrypted original (key in the SQLCipher DB); photos are decoded into memory only. «Очистить» (temporary files) empties `cacheDir` (picker/camera copies) and the in-memory image cache; it never touches `filesDir/media/` (D24) | Nothing readable at rest; the phone's copy is the original |
| D47 | Photo policy | One photo per send; re-encoded as JPEG, long edge ≤ 2560 px, quality 85, orientation applied, **all metadata (EXIF, GPS) dropped**; inline thumbnail 64 px JPEG (≤ 4 KiB). Auto-download default: **Wi-Fi only** (unmetered network); options Wi-Fi / any network / manual. "Save to gallery automatically" default off | Small, private photos; data-friendly default |
| D48 | Upload before envelope | The PENDING message, its attachment and a **held** outbox row are written in one transaction; the envelope is released only after every chunk is on the node. Quota or invalid → the message becomes FAILED; «Повторить» re-signs the `BLOB_META` with the same record id (the blob key is the ciphertext's aad). Node blobs are transient and are **not** part of node backups (D24: the phone's copy is the original) | A receiver never gets a message whose photo isn't there yet |
| D49 | Admin-side node operations | Admin hosts registry `~/.otter-admin/hosts` (`label target [port]`) plus one-command `add-node.sh`, `upgrade-all.sh`, `status.sh` as thin bash wrappers over `otter-admin`, `push.sh`, `upgrade.sh`, `check.sh`. No agent or control channel on the servers. Rolling upgrade one node at a time in manifest order, stops at the first rollback; status is read-only over SSH. 2026-11-12, with the owner (spec approved 2026-11-12) | The owner runs a few nodes from one PC; adding a node or upgrading should be one command and safe to re-run |
| D50 | Backup storage on nodes | A backup is a persistent blob (`BlobMeta.persistent`, no readers, `expires_ms` 0, not deleted by reads) plus a signed `BACKUP_META{version, salt, kdf_m_kib, kdf_t, kdf_p, auth_verifier, blob_key, size}`. The latest version per user wins (tie: later `created_ms`, then record key); the superseded meta record and its blob are deleted on every node (tombstone 30 days). A persistent blob that no `BACKUP_META` references is deleted 7 days after creation (failed uploads, resurrected old blobs). Persistent blobs count toward the 2 GiB quota; at most 3 live ones per user (`QUOTA` beyond). Backup records never age out of the oplog, so a node added later still gets every backup | Backups survive the loss of a hosting; one rule for blob chunks and replication |
| D51 | Restore authentication | `backup.auth` and `backup.fetch` are public. Unknown username or no backup → `salt = HMAC-SHA256(SHA-256("otter/fake-salt/v1" ‖ node private key), username)[:16]` with 65536/3/1, so one node always gives the same answer. `backup.fetch` compares `SHA-256(auth_secret)` in constant time; failures are counted: 5 per username per hour and 20 per day per node → `RETRY_LATER` "too many attempts". A successful fetch grants that connection `blob.get` on exactly that blob. Limits: fake salts differ between nodes, so someone reaching two nodes can tell which usernames have backups (accepted: usernames are visible to every member, the node path is secret); a node the backup hasn't reached yet answers like a wrong password and counts a failure | A phone with only a username and password must find its backup without a login; guessing is slow |
| D52 | Install identity | `PreKeys.installed_ms` (registration or restore time). Per (user, device) the node keeps the newest install: newer → all prekeys deleted and the new `registration_id` stored; equal → merge as before; older → keys ignored (record kept). `auth.login` returns `LoginResponse{registration_id, installed_ms}`. A phone whose `installed_ms` is older than the node's stops syncing and shows `SupersededScreen` (only after its own restore has finished, so a lagging node can't confuse a fresh restore). Installs from before M6 send 0 | The replaced phone must learn it was replaced; the new install must not get old prekeys |
| D53 | Session recovery | New content `session_reset` (`SessionReset{}`), sent 1:1. The restored phone sends it to every contact after uploading prekeys. A receiver inserts a `SYSTEM_RESET` message in the direct chat (if one exists) and deletes every `sender_key_shared` row for that member, so the next group send re-sends our sender key. A 1:1 message that can't be decrypted, or a group message parked for a missing sender key, makes the receiver delete its session with the sender and send `SessionReset`, at most once per contact per hour (`contacts.reset_ms`) | Contacts keep writing with no action on their side |
| D54 | Restore needs the network's address | A wiped phone knows no node. «Восстановить аккаунт» starts with a family invite (any member's QR or a bootstrap link); only its signed manifest is used, the invite is **not** consumed | Same trust root as joining |
| D55 | Backup policy on the phone | Opt-in in Settings; password ≥ 10 chars and zxcvbn score ≥ 3; KDF Argon2id m = 64 MiB, t = 3, p = 1 (BouncyCastle, pure Java); derived `backup_key` and `auth_secret` kept wrapped by the Keystore (`SeedVault`), so automatic backups need no password. Automatic backup while the app is in the foreground when the last success is > 24 h old (no WorkManager); «Создать сейчас»; a password change = new salt, new keys, new version. No media: restored photo messages keep the thumbnail and show «Нет в резервной копии» (`AttachmentState.NOT_IN_BACKUP`) | Simple and honest; sizes stay small |
| D56 | Replaced install is cut off | A gateway session remembers the `installed_ms` it logged in with. Once a newer install's `PREKEYS` is stored for that (user, device), the delivery loop closes the session (WebSocket close "install replaced") and `msg.ack` from it is refused (`UNAUTHORIZED`). A session that uploads the newer `PREKEYS` itself (the restoring phone) raises its own install and is not cut off. 2026-11-12, found in the emulator run | A phone left online while its account is restored elsewhere would otherwise take and ack the new install's mail |
| D57 | Publish-safe repositories | Never in git: `google-services.json`, `fcm*.json`, `*.jks`, `*.keystore`, `*.pem` (except test data), `keystore.properties`, `.env*`, `.dev-mesh/`, `.vm/`, `dist/`, `local.properties`; the admin dir `~/.otter-admin` is outside the repos. `scripts/secrets-check.sh` (both repos) runs gitleaks **v8.24.0** over the whole history (test vectors allowlisted by path in `.gitleaks.toml`) and greps tracked files for private IPv4 addresses (placeholders `192.168.x.y`, `203.0.113.x` and the emulator's `10.0.2.2`/`10.0.2.15` pass), `/home/` and personal e-mail addresses; it must print `secrets check: ok` before publishing. Existing history was rewritten with the owner's OK (2026-11-12, git-filter-repo): author `al <al@users.noreply.invalid>`, `~/` → `~/`. The planned bundle backup before the rewrite was **not** made (M5 notes) | Both repositories can be published without leaking keys, addresses or the owner's identity |
| D58 | Who pushes | A record accepted **locally** (client submit, local import): this node pushes if it is push-capable. A record **replicated from peer P**: this node pushes only if P is not push-capable **and** this node is the first node in manifest order marked `push_capable` (P is the best available approximation of the origin; in a full mesh it is the origin). "Push-capable": for this node, the manifest says `push_capable` **and** an FCM key is loaded; for P, the manifest flag. Push only when the envelope is `urgent`, created ≤ 10 min ago, and the recipient (user, device) has no logged-in, non-replaced (D56) session on this node. Coalescing: ≤ 1 push per (user, device) per 10 s per node. A manifest flag without a loaded key logs a warning at start | One push per message without coordination between nodes; a node that cannot push never silences one that can |
| D59 | FCM message and key | FCM HTTP v1 `messages:send` with `{"token", "android": {"priority": "HIGH", "collapse_key": "otter", "ttl": "600s"}, "data": {"w": "1"}}`: a constant payload, no ids, no content. OAuth2 via `golang.org/x/oauth2/google.JWTConfigFromJSON` (scope `https://www.googleapis.com/auth/firebase.messaging`), project id read from the key file. Key file `/etc/otter/fcm.json` (0640 root:otter); `node.toml` always names it under `[push] fcm_credentials`, and a **missing file means push is off** (re-installing a bundle never breaks or removes push; `otter-node check` parses the key when present, offline). Installed only by `deploy/push-key.sh`, which streams it over ssh stdin (`umask 077`, no temp copy) and expects `push on` in the log after the restart; never in bundles, the admin dir or git. 404 / `UNREGISTERED` → the node deletes that token row locally (if still current); other errors are logged | Google learns only that some device of this project should wake up; nothing to protect in the payload |
| D60 | PUSH_TOKEN record | Payload `PushToken{device_id = 1, kind = FCM, token}` (1–4096 bytes of UTF-8) signed by the account key, sent via `push.register` (`RecordRequest`). Apply: newest `created_ms` per (user, device) wins, ties by record key (migration 0006 adds `push_tokens.created_ms`, `record_key`). Records never expire (one per token change). The app re-sends only when the token differs from the last one a node accepted (`push_token_sent`); it registers once per login, in the background | The token replicates like every record, so any push-capable node can wake the phone |
| D61 | Background model on the phone | One build, no `foss` flavor: `firebase-messaging` is always a dependency, the `google-services` plugin is applied only when `app/google-services.json` exists (never committed; without it `BuildConfig.FIREBASE = false` → no push). `SyncEngine` runs while at least one lease is held: `foreground` (app visible) or `wake` (push, notification action, battery-saver job). A wake: lease → race with a 2 s head start for the last-good endpoint (if it succeeded in the last 7 days) → stop when online, no envelope event for 10 s and nothing due in the outbox (cap 60 s). Push and notification actions enqueue the unique expedited work `wake` (`RUN_AS_NON_EXPEDITED_WORK_REQUEST` when out of quota; on API 26–30 a `dataSync` foreground service with a silent «Проверяем сообщения…» notification). Mode: **FAST** («Быстрые уведомления») when Google Play services + Firebase are available, a token exists and fewer than 3 missed wake-ups in 24 h; else **SAVER** («Экономия батареи»: unique periodic work `saver`, 15 min, network constraint, policy KEEP). A missed wake-up = a session receives an envelope created after the engine last went offline and after the last FCM wake, at least 60 s before this session started (≤ 1 per session); any FCM wake clears the misses. The mode is automatic and only shown in Settings; no «Мгновенно» (persistent connection) mode in V1. Background processes (push, workers, notification actions) load the account before syncing; the mode is applied only once an account exists. WorkManager **2.11.2** (plan: 2.10.1): from 2.11.1 a blocked background network (Android 15) counts as an unmet constraint, so the saver runs as a JobScheduler job that may use the network | Battery first (D7); honest fallback without Google; one APK for everyone |
| D62 | Notifications | Channels «Сообщения» and «Группы» (IMPORTANCE_HIGH) and «Синхронизация» (IMPORTANCE_MIN, for the API < 31 foreground job). One MessagingStyle notification per conversation (id = conversation id) with the last 6 unread incoming messages (photo → «Фото», caption appended as «Фото: …»), grouped under one summary; actions «Ответить» (RemoteInput → outbox) and «Прочитано» (mark read + read receipts), both followed by a wake job; tap opens the chat. `VISIBILITY_PRIVATE` + public version «Otter» / «Новое сообщение». Posted after the receiving transaction commits; none for the chat open on screen; cleared when the chat is read. In-app switch «Показывать уведомления» (default on) and «Настройки Android». POST_NOTIFICATIONS asked once (Android 13+) the first time the chat list is shown. Small icon `ic_stat_otter`, generated by `scripts/export-assets.py` from the monochrome head reframed for 24 dp | Content is decrypted and shown only on the phone; nothing readable on a locked screen |
| D63 | App version | `versionName = "0.5.0"`, `versionCode = 5`; Settings shows «Otter 0.5.0 (abc1234)» at the very bottom, below «Подключение»; the short git hash comes from a Gradle `providers.exec` (`"dev"` when not a git checkout) | Bug reports name the exact build |
| D64 | Otter news, not a service account | News are records signed by a **news key**, not messages from a member account: a real account would need a headless Signal client holding keys, one encrypted copy per member, no history for later members and no verifiable update. Announcements are **signed, not end-to-end encrypted** (nodes can read them): release notes only, never private content. On the phone they are ordinary messages from «Выдра» / "Otter" in an ordinary (not pinned) read-only chat «Новости Выдры» / "Otter News"; the chat is hidden while it has no messages and is dated by its newest announcement (M6.5 emulator run) | Every member, including later ones, sees the same verifiable news |
| D65 | News key | Ed25519, made by `otter-admin news init`, kept in the desktop Secret Service keyring (go-keyring v0.2.6; service `ottermsg-news`, account `network-<first 8 bytes of network_pub, hex>`, value = base64 of the 32-byte seed); the public key is appended to `<admin dir>/news_keys.json` and goes into `Manifest.news_keys = 6` at the next `manifest sign`. A record is valid only while its author key is in the **current** manifest. `news revoke --pub HEX` removes the key and its keyring entry; with the next manifest nodes delete everything it authored and phones delete the messages (and their notification). Claude never asks for or stores a passphrase; the owner types the admin passphrase in their own terminal | The admin key stays out of day-to-day news; one manifest revokes a leaked news key |
| D66 | News records | `ANNOUNCEMENT = 15`: `Announcement{text_ru, text_en, update?}`, each text ≤ 4000 runes, valid UTF-8, at least one non-blank, `expires_ms = 0`; `update = AppUpdate{version_name (1–32 chars), version_code > 0, sha256 (32 B), size (1 B–100 MiB)}`. `ANNOUNCEMENT_DELETED = 16`: `AnnouncementDeleted{target}` (record key author‖id, 32 B), signed by any current news key; kept forever (table `news_deleted`) so a lagging peer cannot resurrect the target; delete only, no edit. A replicated record whose news key is not in this node's manifest is **skipped**, not retried (a revoked key would stall the peer session); `otter-admin` publishes every record to **every** node directly (`news.publish`), and a record no node accepted is not kept in the admin dir. The admin CLI names an announcement by the hex of its 16-byte record id | Small, rare, permanent; revocation can't wedge replication |
| D67 | News delivery and push | `news.list` (logged in) → `RecordBatch` of every stored ANNOUNCEMENT and ANNOUNCEMENT_DELETED, oldest first; event `news` (`Empty`) to every logged-in session when one is accepted or dropped. On a newly accepted, still visible ANNOUNCEMENT created ≤ 10 min ago the node wakes every (user, device) with a push token and no live session here, under the D58 duty rule; deletions never push. Phones verify each record again against the stored manifest, store it as a `NEWS` message in the `NEWS` conversation (DB stays v6), notify (channel «Новости») only for announcements created in the last 3 days, at most one notification update per `news.list`, and clear the notification when the announcement is deleted or revoked | Seconds on FCM phones, ≤ 15 min in battery-saver mode; a new member gets history without a notification storm |
| D68 | APK from the nodes | `otter-node apk import FILE` (does not open the DB) copies an APK to `<data_dir>/apk/<sha256 hex>.apk` (data-dir owner, 0640), keeping the newest 2. `apk.get{sha256, index}` (logged in) → `ApkChunk{data, total_size}` in 1 MiB chunks; unknown hash or index past the end → NOT_FOUND. The app shows «Обновить до X» only when `update.version_code` > its own versionCode, downloads to `cacheDir/apk/<hex>.part` (resumes at chunk boundaries), checks size + SHA-256 (mismatch → file deleted, «Файл повреждён»), and opens the system installer via `ApkFileProvider` (authority `${applicationId}.files`). Release APKs are signed with the owner's release keystore (`keystore.properties` + `*.jks`, gitignored; without them release builds fall back to the debug key); `deploy/release-apk.sh` refuses a debug-signed APK or a versionName/versionCode mismatch. App 0.6.0 / versionCode 6, server 0.6.0 | Updates travel the same censorship-resistant, pinned path as messages |
| D69 | Release dialog, language, links | `deploy/news-dialog.sh VERSION [--apk FILE --version-code N]` reads `dist/news/<VERSION>.md` (sections `## ru`, `## en`, written by Claude from the commits), asks per language «[о]тправить / [и]зменить / [п]ропустить» (edit opens `$EDITOR`, saved back to the draft), then «Отправить? [y/N]» and runs `otter-admin announce`. `upgrade-all.sh` and `release-apk.sh` call it at the end when run from a terminal (`--no-news` skips; a failed or cancelled dialog does not fail the release). The phone shows Russian when its language is `ru`, otherwise English, otherwise whichever text exists. http/https URLs are tappable; a tap shows the full address and asks «Открыть ссылку?» | News go out as part of a release without extra steps; no surprise links |
| D17 | History on phone | **Keep all messages** forever on the phone (no auto-delete). Servers still delete after delivery | User preference; history is also preserved in the password backup |
